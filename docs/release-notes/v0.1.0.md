# Release Note — Aastrika Common Service

## [0.1.0] — 2026-08-10

### Summary

Removes three endpoints confirmed unused by the endpoint-usage audit, and makes the rating
aggregation's silent failure mode visible. The removal cascade eliminates Redis from the service
entirely. Endpoint count drops from 15 to 13; the four in-use rating endpoints and all persistence
behaviour are unchanged.

---

### Security

- New consumer log lines deliberately exclude user ids, and the `NotEnrolledException` is not passed
  to the logger, because its message embeds the user id. `SECURITY.md` 2.5 forbids logging PII at any
  level. Only the activity id and type are logged.
- `spring-boot-starter-data-redis` removed from `pom.xml`, reducing dependency surface. The Tomcat
  CVE override (`pom.xml:33`, TRIAGE T-001) is untouched and still verified by
  `scripts/check-triage.sh`.

---

### Added

- Rating consumer now logs why an event was dropped. `NotEnrolledException` is logged at ERROR with
  the activity id/type before being rethrown so DLQ routing is unchanged; all other failures log with
  a stack trace (`RatingEventConsumer.java`). Previously an event could be rejected and routed to
  `rating.failedRating` with nothing in the console, so `ratings_summary` and `ratings_lookup` would
  silently never update — the failure mode that prompted this release. Note the non-enrolment path is
  non-retryable, but other failures log up to 3 times per record because of
  `FixedBackOff(1000L, 2L)`.
- Postman `R10` documents the enrolment gate: an upsert by a non-enrolled user returns 200 while the
  aggregation drops the event.

---

### Changed

- `ContentClient` is now read-only, serving assessment (content hierarchy) and cohorts (batch lookup)
  only. Constructor drops from 6 parameters to 3.
- `RatingServiceImpl` constructor drops from 8 parameters to 5; `CohortsServiceImpl` from 4 to 3.
- Postman rating requests (`R1`, `R3`, `R4`, `R5`, `R6`) now share collection variables pointing at a
  verified-enrolled user/activity pair. They previously upserted an unenrolled pair while reading a
  third unrelated activity, so the summary could never populate.
- `R1` gained a pre-request script cycling the rating 1..5 — the aggregation is delta-based, so
  re-posting the same value is a silent no-op. Its review is now longer than 100 chars to satisfy
  `REVIEW_MIN_LENGTH` and reach `latest50Reviews`.
- `R4` now asserts `result.response` is non-null, since a missing summary row returns 200 with
  `response: null` and reads as success.
- Stack documentation corrected in `CLAUDE.md`, `SECURITY.md` and `docs/TRIAGE.md` — Redis and
  OpenSearch removed from the data-stores table, persistence notes, infra list and secrets env-var
  list.

### Known Issues

- OpenSearch is now the only unused stack element: no code references it, but `pom.xml:40-42` still
  pulls `spring-data-opensearch-starter`. Left in place because `AastrikaCommonApplication` carries
  Elasticsearch autoconfiguration exclusions that exist solely because that starter is on the
  classpath; removing them risks startup failure. Candidate for a separate change.
- `CourseClient.java:120` logs a raw user id — the same `SECURITY.md` 2.5 violation the new consumer
  logging was written to avoid.
- Stage PostgreSQL is missing `user_program_completion` and `leaderboard_table`, so the certificate
  and leaderboard endpoints return 500 there. The repo has no migration tooling, so schema
  provisioning is manual per environment (see TRIAGE T-002, which requires explicit migrations).
- Stage Kafka points at a hardcoded broker IP (`10.0.137.167:9092`) rather than stable DNS, and uses
  the `dev.rating.event` topic with the same consumer group id as dev. On a shared broker both
  consumers join one group over a single partition, so only one receives events.
- The remote deployment returned 200 from `/ratings/v1/upsert` while writing nothing to the Cassandra
  reachable over the SSH tunnel. Unexplained; reproduce before trusting a 200 from that environment.
- T-004 (weak `sb.api-key` default), T-005 (Cassandra credentials) and T-006 (DB credentials) remain
  open — see `docs/TRIAGE.md`.

### Migration Notes

#### Environment Variables

| Variable | Change | Action Required |
|---|---|---|
| `TOP_PERFORMER_KEYSPACE` | Removed | Delete from deployment config |
| `TOP_PERFORMER_TABLE` | Removed | Delete from deployment config |
| `CONTENT_READ_URL` | Removed | Delete from deployment config |
| `CONTENT_UPDATE_URL` | Removed | Delete from deployment config |
| `CONTENT_SEARCH_LIMIT` | Removed | Delete from deployment config |
| `RATINGS_META_UPDATE_LIMIT` | Removed | Delete from deployment config |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_DB` | Removed | Delete; Redis no longer needs provisioning |
| `CONTENT_SEARCH_URL` | Unchanged | Still required — cohorts batch lookup |
| `CONTENT_HIERARCHY_URL` | Unchanged | Still required — assessment submit |

All removed variables are simply ignored if left set, so config cleanup can lag the deploy.

#### Data / Schema

None. The `user_assessment_top_performer` Cassandra materialized view is no longer read by this
service but is left in place — dropping it is a separate database decision and it may have other
consumers.

#### Config Changes

Redis is no longer a runtime dependency: the service starts and runs with no Redis reachable.
Verified by a clean boot with the Redis starter absent from the classpath.

**Breaking:** callers of the three removed endpoints will receive 404. All three were confirmed
unused before removal.

### Verification

- `mvn clean compile` — BUILD SUCCESS. The only two warnings are pre-existing and in untouched files
  (`ApiRuntimeException.java:8` Lombok hint, `ApplicationExceptionHandler.java` unchecked ops).
- Spring context boots in ~4.4s. No `BeanCreationException`; both persistence units (primary and
  `dataLake`) load; 4 Cassandra repositories found; Kafka consumer assigned `dev.rating.event-0`.
- Endpoint smoke test: summary / `v2/read` / `ratingLookUp` return 200, an invalid rating returns 400,
  and all four removed routes return 404.
- `scripts/check-triage.sh` reports the same 3 completed / 1 open / 2 manual as before the change.
- Not runtime-tested: the new consumer log lines are compile-verified only — they need a rejected
  event to exercise.
